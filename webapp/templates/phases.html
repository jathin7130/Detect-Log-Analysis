how this project is organized

The project runs as ten phases, numbered 0–9, each building on the data, models or infrastructure the previous ones produced. Phases 0–3 build the detection core (environment → data → classical baselines → neural models). Phases 4–5 build supporting infrastructure in parallel with Phase 3 (a fault-injection testbed and a retrieval index), since neither depends on the detectors finishing. Phases 6–9 turn all of that into a working product: a website, an evidence-grounded RCA pipeline with a reliability gate, the website wired to real results, and the final write-up. Every number below is a real measured result, not a placeholder — jump to any phase for the full detail.

Phase 0

Setup

done
Get the environment right before anything else depends on it.

What it does

Creates the Python environment, confirms it points at a real Python installation (not a stub that silently breaks package installs), and confirms the GPU is actually reachable by PyTorch before any training is attempted.

Why it matters

Every later phase assumes two things work: the exact same Python environment every time (so results are reproducible), and the GPU (so neural training finishes in minutes, not days). Checking both before starting is cheap; discovering either is broken halfway through a multi-hour training run is not.

Key steps

  • Virtual environment created, verified against a real python.org install (pyvenv.cfg checked directly)
  • GPU confirmed reachable: torch.cuda.is_available() == True, RTX 4060 detected
  • A persistent tracking checklist set up to log every step as it happens (this is PROGRESS.md in the repo)
Phase 1

Data Pipeline

done
Turn three raw, messy, multi-gigabyte log dumps into clean, labeled, privacy-safe sequences.

What it does

Downloads three public system-log datasets (HDFS, BGL, Thunderbird), strips anything that looks like personal or sensitive information, converts each raw log line into a reusable "template" (the repeating shape of a message, with the changing details like IDs and numbers abstracted out), groups lines into sequences a model can learn from, and locks a fixed split of that data into training/validation/test portions that nothing downstream is allowed to touch until evaluation.

Why it matters

Raw logs are just text — a model can't learn "normal" vs "abnormal" from free text directly at any useful scale. Converting each line into a template id (e.g. "Receiving block <BLK> from <IP>") turns millions of lines into a much smaller vocabulary a model can actually learn patterns over. Masking PII first means none of that learning ever sees a real IP, hostname or credential. And freezing the data split before any model is trained is what makes every later "Model A beats Model B" claim trustworthy — without it, it's easy to accidentally let a model see test data in disguise.

Key steps

  • Download all three datasets in full (HDFS: 11.18M lines, BGL: 4.75M lines, Thunderbird: capped at 10M lines)
  • Mask IPs, hostnames, user@host pairs, file paths and credential-like strings
  • Parse every line into an event template with Drain3 (an algorithm built specifically for this)
  • Build sequences: HDFS groups lines by the storage block they describe; BGL/Thunderbird use fixed 100-event windows (no natural grouping exists for them)
  • Freeze a 70/15/15 train/validation/test split, stratified by label, before any model is trained
What was found:
  • The PII mask caught two real gaps during its own spot-check — HDFS block IDs and Thunderbird install paths were both leaking unmasked into templates. Both fixed before any model saw the data.
  • Final result: 575,061 HDFS sequences (2.93% anomalous), 47,135 BGL sequences (10.24% anomalous), 99,808 Thunderbird sequences (38.36% anomalous) — three very differently-shaped datasets, which turns out to matter a lot later.
Phase 2

Classical Baselines

done
Before trying anything fancy, find out how far simple methods get.

What it does

Trains two well-understood, fast, non-deep-learning anomaly detectors — Isolation Forest (unsupervised: it never sees labels during training) and Random Forest (supervised: it does) — on simple count-based features of each sequence's event templates.

Why it matters

Without this step, there's no way to know whether a later, much more expensive neural model is actually earning its keep. A classical baseline sets the floor: if a neural model can't beat a model that trains in seconds, that's a real finding worth reporting, not an embarrassment to hide.

Key steps

  • Build TF-IDF / template-count features per sequence
  • Train Isolation Forest and Random Forest per dataset (seed 42)
  • Lock the resulting numbers as the permanent comparison point for every model that comes after
What was found:
  • Random Forest essentially solves all three datasets (F1 ≥ 0.982 everywhere) — and does it in 1–13 seconds of training.
  • Isolation Forest is far weaker and wildly inconsistent (F1 from 0.325 to 0.682) — a reminder that "unsupervised" doesn't mean "good," just "doesn't need labels."
  • This floor turned out to matter enormously in Phase 3: the neural models don't always clear it.
Phase 3

Neural Sequence Models

done
The largest phase: LSTM, Transformer, an ablation, cross-domain transfer, drift testing, and the statistics to back every claim.

What it does

Trains two neural sequence models — an LSTM (a recurrent network that reads events in order) and a compact Transformer (which uses attention instead of recurrence) — to predict "what event comes next" given a short window of recent events. When the real next event isn't one the model expected, that's the anomaly signal. Both are trained three times each (different random seeds) per dataset, so results can be reported as an average with a confidence range instead of a single possibly-lucky number.

Beyond that core comparison, this phase also runs five follow-on investigations: an ablation (does adding a semantic text embedding on top of the template id help?), a cross-domain transfer test (can a model trained on one log system say anything useful about a different one?), a drift test (does a model trained today still work if log formats shift slightly tomorrow?), a paired statistical significance test (are two models' scores actually different, or just noise?), and a cost/latency analysis (how much GPU time did each point of accuracy actually cost?).

Why it matters

This is where the project's central question gets answered: is the extra complexity (and extra GPU-hours) of a neural sequence model actually worth it over the classical baselines from Phase 2? And separately — even if a model looks good on the dataset it was trained on, does that tell you anything about how it'll behave on a different system, or on the same system next month after a software update? Both questions matter more to whether this is deployable than the headline accuracy number does.

3.1 — LSTM vs. Transformer: the headline comparison

Window=5 events, top-3 "did the model expect this" scoring, 3 seeds (42/123/777) per dataset per model.

0.265 / 0.271
HDFS F1 (LSTM / Transformer)
0.928 / 0.926
BGL F1
0.823 / 0.815
Thunderbird F1
Finding: the Transformer never meaningfully beats the simpler LSTM on any of the three datasets. And on HDFS specifically, both neural models lose to the simple Isolation Forest baseline from Phase 2 (0.682) — more complexity didn't help here at all.

3.2 — Ablation: does adding semantic text embeddings help?

Compares the plain template-id model against a version that also feeds in a frozen sentence-embedding of each template's text.

0.300 → 0.275
HDFS (template-only → +semantic)
0.932 → 0.927
BGL
0.836 → 0.796
Thunderbird
Finding: adding semantic embeddings doesn't help, and mildly hurts — most clearly on Thunderbird. The template id already captures what the embedding would add, so the extra signal is mostly noise.

3.3 — Cross-domain transfer: does training on one system help on another?

All 6 directed pairs tested (HDFS↔BGL, HDFS↔Thunderbird, BGL↔Thunderbird).

6/6
pairs show 100% vocabulary disjunction
Finding: HDFS, BGL and Thunderbird share zero event templates with each other — they're different enough systems (distributed storage vs. supercomputer hardware vs. general server logs) that nothing learned on one transfers to another at the template level. A subtler finding came from measuring this carefully: a naive accuracy comparison before/after trying to adapt a model to a new system looked identical, which would read as "adaptation did nothing" — except it was a measurement blind spot, not a real result. A different, threshold-independent check showed the model's predictions had, in fact, completely flipped during adaptation. The lesson: a metric that looks unchanged doesn't always mean nothing changed.

3.4 — Drift: does a model stay accurate as logs evolve?

Simulated mild, realistic drift — renamed tokens, a few new log lines, shifted frequencies — on sequences the model had never seen drift in, and measured how often it started false-alarming.

2.6% → 99.9%
HDFS false-alarm rate (37×)
0.4% → 5.4%
BGL (11.7×)
17.3% → 66.0%
Thunderbird (2.8×)
Finding: every model gets measurably worse under mild drift, and HDFS's collapse is dramatic — it ends up flagging almost everything as anomalous. The pattern tracks vocabulary size: HDFS has only 44 known templates, so a small drift has nowhere to "blend in"; BGL and Thunderbird have over a thousand each and are more forgiving.

3.5 — Is "LSTM vs. Transformer" actually a real difference, or just noise?

A follow-up statistical check: for each dataset, both models were scored on the exact same test sequences, then a paired bootstrap test (2,000 resamples) checked whether their F1 difference holds up as a real, repeatable effect rather than random variation.

Finding: on BGL, LSTM and Transformer are genuinely statistically indistinguishable (p=0.073). On HDFS and Thunderbird, the difference is statistically significant (p<0.0001) — but the actual gap is only 0.02–0.03 F1, small enough to be irrelevant in practice. Meanwhile LSTM's gap against Random Forest on HDFS (−0.699) is both significant and large. The takeaway: with a big enough test set, almost any real difference becomes "statistically significant" — the size of the gap still matters more than the p-value alone.

3.6 — Was the GPU time worth it?

13.3s
HDFS Random Forest training
955s
HDFS LSTM training (mean of 3 seeds)
Finding: classical models train 2–3 orders of magnitude faster than the neural ones across all three datasets, and on HDFS/Thunderbird they're simultaneously more accurate too. The neural models' extra cost isn't buying extra accuracy often enough to justify it by cost alone.

A result worth double-checking: was the HDFS comparison fair?

HDFS sequences are much shorter on average (19.4 events) than BGL/ Thunderbird's fixed 100-event windows, so the same window-size-5 setting might be unfair to HDFS specifically. A follow-up sensitivity check re-ran HDFS with a larger window (10) and more lenient scoring (top-5 instead of top-3).

0.300 → 0.545
HDFS LSTM F1 (main config → adjusted)
Finding: F1 nearly doubles with a more HDFS-appropriate setting — so the original "LSTM loses badly to Isolation Forest on HDFS" result was partly an artifact of using one fixed setting across very different datasets. The qualitative conclusion still holds (it doesn't clearly beat Isolation Forest, 0.545 vs 0.682), but "loses badly" overstated it. The main results were deliberately not changed to the better setting — adjusting hyperparameters per-dataset after seeing results would make every other cross-dataset comparison unfair too. This is reported as a limitation instead.
Phase 4

Fault-Injection Testbed

done runs alongside Phase 3
The public datasets have anomaly labels but no known root cause. This phase builds a small system where the cause is always known.

What it does

Stands up four small web services (gateway → orders → inventory / payments) in Docker, wired so a request to "check out" flows through all of them and gets logged realistically at every step. Four kinds of real failures can be deliberately injected into any service on demand — a database connection failure, a slow downstream call, memory pressure, or a full process crash-and-restart — and because the injection is scripted, the exact service, fault type and timing is always known precisely.

Why it matters

HDFS/BGL/Thunderbird can tell you "this looks anomalous" but never "and here's why." Root-cause analysis (Phase 7) needs incidents where the true cause is known, so its diagnoses can actually be checked against ground truth instead of just checked for whether they sound plausible.

Key steps

  • 4 Flask microservices in Docker Compose, logging through the exact same masking + template-parsing pipeline as Phase 1 (no separate code path to maintain)
  • 4 fault types implemented and each individually verified — including confirming a "pod restart" fault actually restarts the container, not just logs a line claiming to
  • An 8-incident scenario run with continuous background traffic, ground truth recorded automatically for every injected fault
What was found:
  • 245 requests, 34 errors, across 280 seconds of the scripted scenario
  • All 8 injected incidents show a clear spike in error/warning log lines at their exact injection timestamp once run through the parsing pipeline — confirming the testbed actually produces usable, diagnosable incidents, not just noise.
Phase 5

Retrieval Layer

done runs alongside Phase 3
Build a searchable memory of every known template and incident, so RCA has something real to cite.

What it does

Converts every known log template (from all three datasets and the testbed) plus every testbed incident description into a numeric "meaning vector" using a small pretrained language model, and indexes all of them for fast similarity search — given a new incident, find the most similar things seen before.

Why it matters

This is what lets Phase 7's language model cite real, specific evidence instead of making things up from general knowledge. Without it, there'd be nothing for an RCA answer to be grounded in.

Key steps

  • 3,360 documents embedded with all-MiniLM-L6-v2 (templates + testbed incidents)
  • A FAISS similarity index built over them
  • Manually sanity-checked with made-up queries to confirm the matches actually make sense
What was found: every test query's top match was clearly correct — e.g. "memory usage is very high" matched the testbed's exact resource-exhaustion log line at 0.714 similarity. The retrieval layer works as intended before it's ever plugged into the RCA pipeline.

Phase 7

RCA + Reliability Gate

done
The part where a language model tries to explain why — and gets checked on whether it's allowed to.

What it does

For a given incident, retrieves the most relevant evidence (Phase 5), asks a local language model (llama3.1:8b, run entirely on this machine — no log data is ever sent to an external API) to diagnose the root cause and say exactly which evidence it's basing that on, then runs the answer through a reliability gate that independently checks two things: did the model actually cite evidence that exists, and is its confidence above a threshold? If either check fails, the gate forces the answer to "abstain" — regardless of what the model itself claimed.

Why it matters

A language model can sound completely confident while being completely wrong, especially when it's missing the information it would actually need. The gate exists because trusting a model's own stated confidence turns out to be a bad idea — shown directly in the ablation below, where removing evidence made the model more confident, not less.

7.1 — Running RCA across 20 real incidents

8 real testbed faults (known cause) + 12 genuine anomalies the trained LSTM actually flagged in HDFS/BGL/Thunderbird (not random windows).

18/20
passed the gate
1/20
gate overrode the model
16/20
judged correct on manual review
Of the 20 cases: 16 were clearly correct, 1 was correct but got conservatively gated to abstain anyway (its confidence just dipped below the threshold), 1 was an honest self-abstain (the model itself said the evidence wasn't enough), and 2 were flagged — both were the same kind of case ("pod restart" faults where only an upstream service's logs were visible), and both got the affected service right but described the symptom rather than the actual crash. That's an explainable gap in what evidence was available, not random error.

7.2 — Does retrieval actually matter, or is it just nice-to-have?

A controlled follow-up: run the exact same 20 incidents again, but tell the model no evidence was retrieved, and see what happens.

90% → 0%
gate answer rate (with → without retrieval)
0.76 → 0.85
model's own confidence (with → without)
Finding: without retrieval, every single attempted answer is unsupported by definition — there's nothing it could have validly cited — and the gate correctly refuses all of them. The model's self-reported confidence went up, not down, once it had less to go on — the opposite of what you'd want, and exactly the behavior that makes an external, independent check necessary rather than optional.

Phase 9

Write-up & QA

done
Turn results into a document someone else can actually read and trust.

What it does

Consolidates every phase's findings into a single written report, documents every place the plan changed from what was originally proposed (and why), and does a final pass checking that every number in the write-up actually matches the underlying result file it claims to summarize.

Why it matters

Results scattered across dozens of output files aren't a thesis. And a write-up nobody has fact-checked against its own source data is asking a reader to trust it blind.

Key steps

  • Full results narrative written, organized by phase, with every scoping decision explicitly tabulated
  • requirements.txt audited against what the code actually imports
  • A full audit pass: every number quoted in the write-up cross-checked line-by-line against the result file it came from
  • Follow-up gap-closing work: paired statistical significance tests, a consolidated cost/latency table, and the with/without-retrieval ablation above — all three were identified as missing during review and closed before the write-up was finalized
